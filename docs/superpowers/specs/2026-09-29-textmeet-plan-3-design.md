# TextMeet — План 3 (расшифровка): решения

**Дата:** 2026-09-29
**Основа:** [спецификация](2026-09-25-textmeet-design.md) §3.3, §5.2, §5.4, §5.5, §5.6, §6, §7; [итоги спайка](../spike-results.md)
(§1, §5, §6 — открытые вопросы); [проверки Плана 2](../plan-2-checks.md); [макет](https://claude.ai/artifact/Urmc3atvSFifUpDyBzjeR6)
(лист 1 — текст встречи и список, лист 6 — настройки «Расшифровка»).
**Согласовано с пользователем 2026-09-29:** всё, что видно в программе (§2); автоматическое определение числа людей —
собственная группировка голосов (§4.4), вопрос о числе участников остаётся необязательным; во время новой записи
расшифровка не останавливается, а замедляется (§5.3). Созвоны — на 95% в наушниках, поэтому защиты от эха
(голоса собеседников на дорожке «Я») в первой версии нет, как и записано в спецификации §4.

## 1. Что входит в План 3

- Менеджер моделей: реестр (файлы, адреса, размеры, SHA-256), скачивание с докачкой, повторами и проверкой,
  раздел настроек «Расшифровка» (модель, скачанные модели, «Удалить»).
- Процесс расшифровки (`utilityProcess`), очередь встреч в main, прогресс, перезапуск после падения, сторож зависания,
  продолжение после выхода из программы.
- Конвейер: дорожка «Я» (детектор речи → GigaAM), дорожка собеседников (разделение по голосам → реплики без наложений
  + речь между репликами → GigaAM), запись без звука компьютера (всё — «Спикер N»), слияние в `transcript.json`.
- Автоматическое определение числа собеседников (§4.4) — закрывает открытый вопрос спайка про порог.
- Показ готового текста во встрече (только чтение), «Расшифровать» / «Расшифровать заново» / «Повторить»,
  уведомление «Текст встречи готов».

**Не входит:** переход по клику к месту записи, правка текста, переименование спикеров, поиск, удаление (План 4);
импорт файла (План 5, но одноголосый путь конвейера делается здесь — он нужен записи без звука компьютера); Whisper
(План 7 — в настройках его пока нет); защита от эха. Отложенное из Плана 2 («Готовим…» у старых встреч с ошибкой,
замена окна «Запись остановлена») — в Плане 4, как записано в [проверках](../plan-2-checks.md).

## 2. Интерфейс

- **После «Стоп».** Окно «Запись остановлена» — как в Плане 2. «Расшифровать» и «Пропустить» оба ставят встречу в
  очередь; «Пропустить» = число участников не указано (`participantsHint = null`), программа определит сама.
  Подсказка под вопросом остаётся прежней.
- **Список встреч.** Пометки: «в очереди», «расшифровка 62%», «ошибка расшифровки» (как в макете). Готовая встреча —
  без пометки.
- **Встреча во время расшифровки.** Вместо текста — блок с этапом и полоской прогресса: «Скачиваем модель
  расшифровки — 120 из 360 МБ», «Готовим звук», «Расшифровываем вашу речь», «Разделяем собеседников по голосам»,
  «Расшифровываем собеседников»; для встречи в очереди — «В очереди на расшифровку». Плеер работает.
- **Готовый текст** — как на листе 1 макета: строка «время · спикер · текст» (Literata), «Я» для владельца,
  «Спикер 1», «Спикер 2»… по порядку первого появления. Только чтение.
- **Кнопки во встрече:**
  - «Расшифровать» — у встречи без текста в статусе `recorded` (восстановленная после сбоя; записи Плана 2,
    сделанные до расшифровки; окно «Запись остановлена» закрыто выходом из программы). Автоматически такие встречи
    в очередь не ставятся.
  - «Расшифровать заново» — у готовой встречи и у встречи в очереди/в работе: окно с вопросом о числе участников
    (тот же блок кнопок 2–6 / «другое», что в окне «Запись остановлена»), «Отмена» / «Расшифровать». Текст заменяется,
    когда новая расшифровка закончится; до этого виден старый. Если встреча сейчас расшифровывается — работа
    прерывается и начинается заново.
  - «Повторить» — у встречи с ошибкой расшифровки, рядом с понятной причиной.
- **Уведомление «Текст встречи готов»** (название встречи), только если главное окно скрыто или не в фокусе;
  щелчок открывает окно на этой встрече. При ошибке — «Не удалось расшифровать встречу».
- **Настройки → «Расшифровка»** (лист 6 макета без Whisper): «Модель — GigaAM v3» с описанием и состоянием
  («скачана · 330 МБ» / «скачается при первой расшифровке»); «Скачанные модели» — строки «GigaAM v3 · 330 МБ» и
  «Разделение по голосам и поиск речи · 33 МБ» с «Удалить» (недоступно, пока идёт расшифровка) и пояснение
  «Удалённая модель скачается заново при следующей расшифровке».

## 3. Данные

### 3.1 `transcript.json` (новый файл в папке встречи, пишется атомарно)

```ts
{
  schemaVersion: 1,
  model: 'gigaam-v3-e2e-rnnt',
  createdAt: string,                 // ISO
  speakers: [{ id: 'me' | `s${n}`, kind: 'me' | 'other' }],   // имена — в meeting.json.speakerNames (План 4)
  segments: [{ id: string, start: number, end: number, speakerId: string, text: string, edited: boolean }],
}
```
- Время — в секундах от начала встречи (начала самой ранней дорожки; сдвиг дорожки `startOffsetMs` прибавляется),
  то же начало, что у `mix.opus`.
- Схема zod — `looseObject`, как у `meeting.json` (незнакомые поля сохраняются).
- Реплики с пустым текстом не пишутся.

### 3.2 `meeting.json`
Новых полей нет. Переходы статуса: `recorded` → `queued` → `transcribing` → `done` | `error` (+ `errorMessage`).
`model` заполняется при успехе. Прогресс на диск не пишется — он только в памяти main (чтобы не переписывать файл
в OneDrive дважды в секунду).

## 4. Конвейер (процесс расшифровки)

### 4.1 Какие дорожки как обрабатываются

| Встреча | Дорожка «Я» (`mic`) | Вторая дорожка / единственная |
|---|---|---|
| Запись с «Звуком компьютера», участников 2 | детектор речи → «Я» | `system`: детектор речи, **без** разделения → «Спикер 1» |
| Запись с «Звуком компьютера», участников ≥ 3 | детектор речи → «Я» | `system`: разделение на N − 1 голос |
| Запись с «Звуком компьютера», не указано (или указан 1) | детектор речи → «Я» | `system`: разделение, число — автоматически (§4.4) |
| Запись без «Звука компьютера» (живая встреча) | — | `mic`: разделение на N голосов или автоматически (указан 1 — без разделения); все — «Спикер N» |
| Дорожка `system` пустая / не записалась | детектор речи → «Я» | — |

### 4.2 Шаги
1. **Подготовка.** ffmpeg (встроенный, с пониженным приоритетом) → 16 кГц моно float32 в stdout. Буфер выделяется
   сразу по длительности встречи (+5 %) и при нехватке растёт удвоением — пик памяти ≈ 1× звука дорожки, а не 3×
   (замечание спайка). Дорожки обрабатываются по очереди; звук первой освобождается до чтения второй.
2. **Детектор речи** (Silero VAD, `enableExternalBuffer = false`): порог 0,5, тишина ≥ 0,5 с, речь ≥ 0,25 с,
   кусок ≤ 20 с. Соседние куски одного спикера с паузой ≤ 1 с склеиваются в реплику (не длиннее 60 с).
3. **Разделение по голосам** (pyannote segmentation 3.0 + eres2net, как в спайке; `minDurationOn 0,2`,
   `minDurationOff 0,5`): с числом голосов — кластеризация библиотеки на ровно столько; без числа — §4.4.
4. **Реплики без наложений** (§4.5) и **речь между репликами** (§4.6).
5. **Склейка** соседних ходов одного спикера с паузой ≤ 1 с; **резка** реплик длиннее 20 с на куски по самому
   тихому месту (как в спайке, `splitAtQuietPoints`); кусок короче 0,1 с не распознаётся.
6. **Распознавание** GigaAM v3 e2e rnnt, кусок за куском; текст кусков реплики соединяется пробелом.
7. **Слияние**: реплики обеих дорожек сортируются по началу, нумеруются, пишутся в `transcript.json`.

### 4.3 Интерфейс движка
Как в спецификации §5.4 (`AsrEngine`); в Плане 3 одна реализация — GigaAM. Детектор речи и разделение по голосам —
отдельные маленькие модули с тонкими интерфейсами, чтобы логику §4.4–4.6 можно было проверять без нативного кода.

### 4.4 Число собеседников, если оно не указано
Опыты 2026-09-29 (запись на двоих, 15,6 мин; её половины по одному голосу; открытая запись четырёх человек из релизов
sherpa-onnx, 55 с):

| Способ | 2 человека | 1 человек | 4 человека |
|---|---|---|---|
| Встроенный порог библиотеки 0,5 / 0,7 / 0,9 / 1,1 / 1,3 | 72 / 40 / 21 / 6 / 1 | — | — |
| Собственная группировка, сходство 0,5–0,7 | **2** (совпадение с одобренным разделением 96–98 %) | **1** | **4** |

Алгоритм:
1. Библиотека разделяет с `numClusters = −1` и порогом 0,5 — намеренно дробит, но даёт точные границы ходов.
2. Для каждого хода — «отпечаток голоса» (eres2net, `SpeakerEmbeddingExtractor`) по первым ≤ 15 с хода
   (~15 с работы на 15 мин записи).
3. Ходы ≥ 0,5 с группируются: пока у двух групп косинусное сходство центров (центр — сумма нормированных отпечатков
   с весом длительности) ≥ **0,6**, самые похожие объединяются. Группы создают не больше 400 ходов: если их больше —
   самый длинный ход из каждого из 300 равных окон встречи и 100 ходов, самых непохожих на уже выбранные (иначе на
   интервью голос с одними короткими вопросами не создал бы группы и исчез; остальные ходы получают ближайшую группу
   в п. 5). Сходства хранятся в таблице с ближайшим соседом каждой группы — на многочасовой встрече группировка идёт
   доли секунды, а не минуты (замечание ревью прототипа). Нулевой или испорченный (NaN) отпечаток считается отсутствующим.
4. Группы, у которых речи меньше **min(20 с, 10 % всей речи дорожки)**, растворяются: это почти всегда обрывки
   одного из крупных голосов. Если крупных нет — остаётся одна самая большая группа.
5. Каждый ход (и короткие < 0,5 с) получает ближайшую по сходству из оставшихся групп.

Ограничение: человек, сказавший на длинной встрече меньше 20 с, припишется похожему голосу; исправление —
«Расшифровать заново» с числом участников. Окно «Запись остановлена» и так советует число указать.

### 4.5 Реплики без наложений (открытый вопрос спайка: перекрытия распознаются дважды)
- Ход короче 1,5 с целиком внутри чужого («угу», «да») отбрасывается.
- Время делится на участки между границами всех ходов; на участке, где звучат несколько ходов, вложенный ход
  побеждает накрывающий (A делится на «A до B» и «A после B»), остальным участок делится поровну по порядку начала
  (два частично наложенных хода — граница посередине общего участка).
- Соседние куски одного спикера сливаются.
Итог — ходы не пересекаются (проверено и на 3000 случайных наборах), каждый участок звука распознаётся один раз. Наложения между дорожками «Я» и
собеседников не убираются: это разные люди на разных дорожках.

### 4.6 Речь между репликами (открытый вопрос спайка: звук вне ходов теряется)
Детектор речи прогоняется и по дорожке собеседников. Участки речи ≥ 0,5 с, не покрытые ни одним ходом, становятся
ходами спикера ближайшего по времени хода, затем — склейка по §4.2 п. 5.

## 5. Очередь и процесс расшифровки

### 5.1 Очередь (main)
- Одна встреча за раз, по порядку постановки. Очередь — это встречи со статусом `queued` в библиотеке; при запуске
  программы встречи в `queued` и `transcribing` снова ставятся в очередь (`transcribing` начинается заново).
- Библиотека встречи фиксируется при постановке (как у сведения в Плане 2: `{libraryDir, id}`).
- Расшифровка не ждёт сведения `mix.opus`: она читает дорожки.
- Если папка встречи исчезла — задача молча снимается (в журнал).

### 5.2 Процесс (`utilityProcess`)
- Запускается при первой задаче, остаётся жить между задачами, закрывается через 5 минут простоя (освобождает
  ~1 ГБ памяти моделей).
- Сообщения main → процесс: `transcribe {jobId, tracks, participantsHint, modelsDir, threads}`, `setThreads`. Процесс → main: `progress {jobId, stage, fraction}`, `done {jobId, transcript}`, `failed {jobId, message}`.
  Все сообщения проверяются zod с обеих сторон.
- `transcript.json` пишет main (атомарно), а не процесс.
- **Падение процесса** → встреча `error` «Расшифровка прервалась из-за сбоя», процесс перезапускается для следующей.
- **Зависание:** сторож в main — нет сообщений дольше max(10 мин, 0,5 × длительность встречи) → процесс
  убивается, встреча `error` «Расшифровка зависла». Пока идёт разделение по голосам, срок — в 6 раз больше оценки
  этого шага по длине звука (верно и для восстановленной записи, у которой длительность ещё неизвестна).
- **Выход из программы** во время расшифровки: процесс закрывается, встреча остаётся «расшифровывается» и
  продолжается при следующем запуске (ошибкой не помечается). Выход убитого процесса, пришедший позже, и его
  сообщения к следующей задаче не относятся. (Разделение по голосам — один долгий вызов без прогресса:
  ~2,5 мин на 15 мин записи; прогресс на этом этапе main досчитывает по времени, до 95 % этапа.)
- **Отмена** («Расшифровать заново» во время работы, выход) — процесс убивается и перезапускается; это надёжнее,
  чем прерывать нативный вызов.

### 5.3 Нагрузка
- Приоритет процесса расшифровки — ниже обычного (`os.setPriority`), всегда.
- Потоков: `min(8, ядер − 1)`; во время записи — 2. Смена числа потоков вступает в силу со следующего куска
  распознавания (распознаватель пересоздаётся, ~1 с) и со следующей дорожки для разделения по голосам.

### 5.4 Прогресс
Доля по этапам пропорционально ожидаемому времени: подготовка 5 %, «Я» 35 %, разделение 25 %, собеседники 35 %
(веса пересчитываются, если этапа нет). В main — не чаще 2 раз в секунду в окно.

## 6. Модели

- **Реестр в коде:** GigaAM v3 e2e rnnt (4 файла, ~330 МБ), pyannote segmentation 3.0 (~6 МБ), eres2net (~26 МБ),
  Silero VAD (~0,6 МБ): адрес, размер, SHA-256 (берутся из Hugging Face / GitHub при написании плана и
  проверяются тестом реестра).
- **Папка:** `%LOCALAPPDATA%\TextMeet\models` / `~/Library/Application Support/TextMeet/models` — та же, что в
  спайке; версия для разработки пользуется той же папкой (модели большие, данные в них не меняются); тесты —
  временной папкой через `TEXTMEET_MODELS_DIR`. Уже лежащие
  файлы проверяются по SHA-256 один раз, результат запоминается (`verified.json`: имя, размер, время изменения).
- **Скачивание:** в `*.part`, докачка через `Range`, тайм-аут 30 с без данных, 3 повтора с паузой, проверка размера и
  SHA-256, затем переименование. Неверная сумма → `.part` удаляется, ошибка «Файл модели повреждён». Одна загрузка за
  раз; прогресс в байтах → этап «Скачиваем модель».
- **Удаление** из настроек — только когда расшифровка не идёт.

## 7. Ошибки

| Ситуация | Что видит пользователь |
|---|---|
| Нет интернета / сервер не отвечает при скачивании | «Не удалось скачать модель расшифровки: нет связи с сервером» + «Повторить» |
| Неверная сумма / размер модели | «Файл модели повреждён, он будет скачан заново» + «Повторить» |
| Мало места для модели | «Не хватает места на диске для модели (нужно 360 МБ)» |
| Дорожка не читается ffmpeg | «Не удалось прочитать запись: …» + «Повторить»; если читается хотя бы одна дорожка — расшифровка идёт по ней, в тексте нет реплик другой |
| В записи нет речи | Встреча `done`, вместо текста — «В записи не найдено речи» |
| Падение / зависание процесса | §5.2 |
| Папка встречи пропала | Задача снимается (журнал) |

Подробности и коды — в журнал; текста встречи в журнале нет.

## 8. Тестирование

- **Модульные (Vitest):** реплики без наложений, речь между репликами, склейка и резка, группировка голосов (§4.4)
  на синтетических отпечатках, выбор пути по дорожкам (§4.1), прогресс, очередь (порядок, продолжение после
  запуска, отмена, падение, зависание — с подменным процессом), реестр и скачивание (локальный HTTP-сервер: докачка,
  обрыв, неверная сумма, тайм-аут), схема `transcript.json`, тексты.
- **Интеграционные (реальные модели, локально и в `ci` с кешем моделей):** эталонная запись GigaAM → ожидаемый текст;
  запись четырёх человек → 4 спикера; две дорожки → «Я» и «Спикер 1» по порядку.
- **Сквозные (Playwright):** подменный движок (`TEXTMEET_TEST_ASR=fake`: мгновенный «текст» по длительности кусков)
  — запись → «Расшифровать» → текст во встрече; «Расшифровать заново»; ошибка → «Повторить»; продолжение после
  перезапуска программы.
- **Ручная проверка** на Windows и Mac: созвон вдвоём, втроём (или видео с несколькими голосами), живая встреча без
  звука компьютера, скачивание моделей на Mac с нуля, выход во время расшифровки, расшифровка во время новой записи.
